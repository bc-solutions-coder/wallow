# Unified Plan — TanStack Start Adoption + SDK Streamlining

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan
> task-by-task. Phases are strictly ordered; tasks within a phase are ordered unless marked
> parallel-safe. Every phase ends with a hard gate — do not start the next phase on a red gate.

**Goal:** All three React apps become real TanStack Start applications consuming a
framework-neutral, mostly-generated SDK — no hand-rolled SSR host, no h3, no module-global
client singleton, no hand-written query layer — so a fresh fork gets a working, secure app from
"install the SDK, add `tanstackStart()`, mount the splat server routes, write feature screens."

**Architecture:** The SDK's server entry ports from h3 `EventHandler`s to web-standard
`Request → Response` handlers (its BFF/proxy/session core stays hand-written — that is the
product). Apps mount those handlers via Start file-based server routes and consume a
per-request `createWallowSdk()` client on the server, a boot-created instance in the browser.
`@tanstack/react-router-ssr-query` solely owns SSR dehydration. The operation + query surface
is generated by hey-api (`@hey-api/sdk` + `@tanstack/react-query` plugins).

**Tech Stack:** .NET 10 (OpenAPI transformers), `@hey-api/openapi-ts@0.99.0`,
`@tanstack/react-start` + `@tanstack/react-router` (pinned exact, current latest),
`@tanstack/react-router-ssr-query`, Nitro (opt-in Vite plugin, **beta** — see V3/D9) for the
Node/Docker server, Vite 8, TanStack Query v5.

## 3. Decision log (collision resolutions)

- **D1 — h3 is removed from the SDK.** `packages/sdk/src/server/**` goes web-standard
  `Request → Response`. `iron-webcrypto` stays a **direct** dependency (this inverts 0928's
  "import iron through h3" small-win, which only made sense while h3 remained). Apps drop h3
  entirely in Phase 3 when their hosts are deleted.
- **D2 — SDK surface collapse comes AFTER the Start migration** (0909's ordering wins over
  0928's). Query-plugin adoption churns feature files; the migration churns app shells;
  separating them keeps each diff reviewable and each gate meaningful. The only SDK work that
  precedes migration is what the migration consumes: web-standard handlers, `createWallowSdk`,
  SSR-safe auth redirects, server presets, and the browser `WallowError` export (Phase 2).
- **D3 — `@tanstack/react-router-ssr-query` solely owns dehydration.** The SDK ships **no**
  dehydration/hydration code, ever. wallow-web's JSON-string workaround and the absent
  hydrate wiring in wallow-auth/minimal-app are all replaced by the integration.
- **D4 — one SSR request-context design.** The SDK ships per-request primitives
  (`createWallowSdk(options)`); Start's global request middleware is the only consumption
  site: it builds the per-request SDK from `getRequest()` and places it in router context.
  `internalOrigin` (container self-fetch origin) is a **transport concern inside the SDK's
  custom fetch** — `baseUrl` stays byte-identical between server and browser so generated
  query keys (which embed `baseUrl`, V5) hydrate correctly. `setSsrRequestContextResolver`,
  `configureSsrClient`, and the AsyncLocalStorage seam are deleted in Phase 4.
- **D5 — no `createPassthroughProxy` extraction into web-shell.** The passthrough preset
  ships from the **SDK server entry** (task 2.7) and is consumed by server routes;
  web-shell's server layer is deleted wholesale.
- **D6 — Start's session/CSRF utilities are not used in the SDK.** The SDK stays portable;
  its session/CSRF core is the audited product. We steal the lesson only: explicit iron
  `ttl` (task 0.6).
- **D7 — query keys**: adopt generated flat keys + `queryKeys: { tags: true }`; keep one
  small curated `invalidations.ts` for subtree sweeps (matching on `_id`/tags). The
  CLAUDE.md/frontend-state rule rewrite lands **in the same change** as key adoption
  (task 4.1).
- **D8 — server routes use a single `ANY` handler** on splat routes (V2).
- **D9 — hosting is Nitro-on-Vite** (`nitro()` plugin). **RESOLVED by the task 3.0 spike:
  all four container checks passed (boot, hashed-asset serving, `PORT`, clean SIGTERM), so
  Nitro is ADOPTED and the fallback is not taken** — task 3.4 keeps its full web-shell
  deletion scope and no "re-evaluate Nitro" follow-up bead is needed. Nitro is still
  `3.0.260610-beta` with no stable release, so pin it exactly and treat any bump as a change
  that re-runs those container checks. (The unused fallback was: keep web-shell's standalone
  host serving Start's `dist/` output, defer that slice of 3.4, file a re-evaluation bead.)
- **D10 — epic sequencing**: this plan's Phases 3–4 must not overlap `Wallow-m5aq`'s
  app-sweep phases on the same app. Coordinate via beads before claiming either.
- **D11 — E2E safety net re-established in Phase 0** (task 0.11, V10), before any SDK or
  app churn — so the Phase 2 gate already has a green suite (with a recorded quarantine
  list) to compare against.
- **D12 — no standalone "fix the comment" task.** `bff-server.ts:17-34` is narrowly
  accurate about the named API but stale and materially misleading about the capability —
  V1 disproves its "no server-route factory" conclusion at the file's own pin
  (`bff-server.ts:20-27`). The comment is corrected in-flight while 2.4 touches the file;
  the file itself dies in 3.3.
- **D13 — acknowledged temporary scaffolding**, each marked `// TEMPORARY` with a bead:
  - **a)** Phase 2's h3 compatibility shim exists **only in wallow-web's**
    `bff-server.ts` (~10 lines wrapping the web handlers back into the existing h3 host,
    V9); deleted by 3.3.
  - **b)** Phase 3.3 keeps a **temporary `setSsrRequestContextResolver` bridge** in
    wallow-web's `src/start.ts` (V17) so SSR data keeps flowing between the host deletion
    (Phase 3) and the seam deletion (task 4.4).
  - **c)** Phase 1.4 permits thin local aliases for renamed operations **only in files
    already scheduled for deletion in Phase 4**.
- **D14 — client instance model.** In the **browser**, the app creates **one** SDK instance
  at boot (module scope in app code — the SDK itself holds no global). On the **server**,
  request middleware creates a per-request instance. Generated operations receive the
  instance via the standard `{ client }` call option. `src/runtime-config.ts` **survives**
  Phase 4 as the home of the `WallowError` response interceptor; only its baked `/api`
  default dies (2.5 makes `baseUrl` explicit). The interceptor is *defined* in
  `runtime-config.ts`; **`createWallowSdk` registers it on every instance it creates** —
  the generated default client is never used directly by app code.
- **D15 — release train.** The SDK publishes (`sdk-v*`) only at the **Phase 3 and Phase 4
  gates**, never mid-phase — intermediate `!` commits accumulate into those two releases.
  `!` is reserved for genuine consumer-visible contract breaks (SDK server/browser contract,
  web-shell server removal, **and fork-visible backend configuration contracts** — 0.1's
  seed-client removal, 0.3's public-client flag); mechanical internal churn is `refactor:`.
  The platform (root, 4.x) absorbs the whole migration as at most one major. **Version
  math:** `release-please-config.json` sets no `bump-minor-pre-major` for the sdk (the v5
  action defaults it false), so the first `!` release takes the SDK from 0.2.0 straight to
  **1.0.0**. This lands at the Phase 3 gate and is **accepted deliberately** — the
  web-standard server contract *is* the 1.0 surface — rather than fought with config.

### Task 2.2 — Port `server/handlers.ts` to web-standard

**Files:** `packages/sdk/src/server/handlers.ts` (446 lines) + `handlers.test.ts` (875).
**Steps:** Replace h3 accessors (`getCookie`/`setCookie`/`getQuery`/`sendRedirect`/…) with

## Explicitly correct as-is — do not "simplify" (carried from 0928)

Recorded so no phase of this plan churns them:

- **`server/proxy.ts` core logic** — silent OIDC refresh under a distributed lock, reactive
  retry on upstream 401, detection of .NET cookie-auth challenges disguised as 3xx, bounded
  `Retry-After` honoring, verbatim RFC 7807 passthrough. No library does this combination.
  (Phase 2 ports its *transport*, never this logic.)
- **CSRF double-submit validation** — `timingSafeEqual` with length pre-check; an empty
  header never satisfies a present session token.
- **Session cookie chunking** — indexed cookies under a size cap, stale higher-index chunks
  cleared. (2.1 spike proves it survives the port.)
- **`server/oidc.ts`** — thin over `openid-client`; `rewriteOrigin` is a real OpenIddict
  requirement.
- **`SessionStore` + node-redis adapter** — `withRefreshLock` (`SET NX EX`) is the
  load-bearing method; `unstorage` has no equivalent.
- **`packages/styles/branding.ts`** — renders the theme block per request for per-client
  `themeJson` overlays; not build-time codegen.
- **`packages/testing`**, **`packages/ui` primitives**, **`use-is-desktop.ts`**,
  **`resolveSsrInternalOrigin`** (its *logic* — which 2.5 ports into `internalOrigin`).

web-shell's host runtime is deliberately **not** on this list — it is deleted (3.4), but its
recorded reasoning is ported across during migration, not rediscovered.
