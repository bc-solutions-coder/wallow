# GitHub workflow mechanics for the CI lifecycle design

Investigated 2026-09-06 for [Choose the workflow layout and fork setup contract](https://github.com/bc-solutions-coder/wallow/issues/212). Planning evidence only; no workflows or settings changed.

## Required validation

GitHub strict checks require the PR branch to be current with its base. Merge queues instead require the validation workflow to handle `merge_group`; `pull_request` and `push` alone do not report the queue's required check. Both approaches can enforce validation against integration changes; they are different setup contracts. Sources: [protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [required-check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

A skipped workflow can leave a required check pending, whereas a conditionally skipped job counts as success. A dependent job skipped after upstream failure can therefore fail to block merging. GitHub recommends `always()` with `needs` for dependent required checks. Design inference: use one stable, unfiltered aggregate check that explicitly examines all expected results and accepts skips only for deliberately unaffected work; fail on failure, cancellation, or missing required evidence. Keep this aggregate short and free of checkout/network work. `always()` jobs can continue during cancellation, so cancellation must never become a green aggregate merely because its shell command ran successfully. Sources: [required-check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks), [cancellation mechanics](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-cancellation).

## Artifact identity and expiry

Logs and artifacts default to 90-day retention, configurable per artifact within repository/organization limits. Workflow re-runs are available for 30 days and retain the original SHA/ref and original actor privileges. Retention and retry windows are distinct. Design inference: missing/expired exact outputs must stop promotion; regenerate and validate at the exact revision to create new evidence instead of silently substituting a different build. Sources: [artifact retention](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/remove-workflow-artifacts), [re-runs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs).

The artifact API exposes artifact ID, digest, expiry and producing run ID/repository/head SHA. Bind these to the expected trusted workflow, successful run, revision and output manifest. A download digest confirms integrity, not authorization to publish; explicitly fail mismatches rather than relying only on the download action's warning. Sources: [artifact REST API](https://docs.github.com/en/rest/actions/artifacts), [artifact transfer and validation](https://docs.github.com/en/actions/tutorials/store-and-share-data). This is a design inference, not a claim that metadata alone makes promotion safe.

## Release automation token

Current GitHub docs have a newer exception than release-please's README: `GITHUB_TOKEN` PR opened/synchronize/reopened events create approval-required workflow runs; App installation tokens or PATs allow automatic triggering. Other token-created events generally do not trigger workflows, except workflow/repository dispatch. Thus release tags/releases created using `GITHUB_TOKEN` must not be assumed to launch independent release-event workflows. Choose App authentication for automatic release-PR CI and release-event fan-out, or explicitly orchestrate publication using action outputs/dispatch and document PR approval requirements. Sources: [GitHub event triggering](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow), [release-please action](https://github.com/googleapis/release-please-action), [App setup](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/making-authenticated-api-requests-with-a-github-app-in-a-github-actions-workflow). GitHub's service documentation takes precedence over the README's older blanket suppression wording.

## Concurrency and mutable aliases

Concurrency permits one running job/run per group. The default allows one pending run and replaces older pending work. Current syntax also supports `queue: max`, up to 100 pending runs, incompatible with `cancel-in-progress: true`. FIFO is by time entering the concurrency wait, not dispatch time; GitHub explicitly does not guarantee overall ordering. Sources: [concurrency syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [concurrency overview](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency).

Design inference: serialize the complete mutable publication critical section, but also check freshness under that serialization immediately before updating each alias or docs deployment. Old workflow retries can enter later and must not roll aliases backward. Immutable version/digest publication can be independently retryable; matrix `max-parallel` or a concurrency group alone cannot enforce monotonic release identity. All writers for the same target must share the group; external/manual writers need their own coordination contract.

## Follow-up: CodeQL, package promotion, and scan coverage

CodeQL `analyze` supports `upload: never`, including failure paths, and `upload-database: false`; it exposes the SARIF directory. This permits a proposed read-only analysis job and a separate optional uploader without putting a security-events writer in compilation. Validate the pinned action's read-only behavior during implementation: its documented token input still describes security-events permission for the normal upload path, and the action has status reporting/caching behavior beyond SARIF. Analysis execution success is distinct from findings policy: GitHub code-scanning merge protection separately evaluates tool completeness and configured alert severity. If reporting is optional, a local SARIF policy evaluator must enforce the agreed severity independently of upload. Sources: [analyze inputs](https://github.com/github/codeql-action/blob/main/analyze/action.yml), [analysis implementation](https://github.com/github/codeql-action/blob/main/src/analyze-action.ts), [merge protection](https://docs.github.com/en/code-security/concepts/code-scanning/merge-protection).

Public GitHub repositories support code scanning; private repositories require an eligible organization and Code Security entitlement. The underlying CodeQL CLI has separate usage terms: disabling upload does not bypass licensing. Thus a universal secret-free private-fork contract cannot silently require CodeQL without checking eligibility; state unsupported analysis explicitly or select an approved alternative. Sources: [CodeQL action license](https://github.com/github/codeql-action#license), [private-repository availability](https://docs.github.com/en/code-security/reference/code-scanning/troubleshoot-analysis-errors/private-repository-enablement).

`pnpm pack` creates a tarball and runs prepack/prepare/postpack scripts. Keep packing in the unprivileged build job. `npm publish ./verified.tgz --ignore-scripts --registry=<approved registry>` publishes an existing tarball with scripts disabled; run outside any source workspace with controlled client config and explicit destination, then verify the registry's exact package/version integrity against the retained tarball. npm submits SHA-512 integrity on publication and refuses duplicate name/version publication. An existing version should count as a successful retry only after a matching integrity comparison; missing or differing metadata must fail. Sources: [pnpm pack](https://pnpm.io/cli/pack), [npm publish](https://docs.npmjs.com/cli/v11/commands/npm-publish/), [ignore-scripts](https://docs.npmjs.com/cli/v11/using-npm/config/#ignore-scripts). Command details and integrity comparison are a design inference; exercise the pinned client and target registry before claiming retry behavior works.

Trivy documents local Docker-format image tar files and OCI-layout directories through `image --input`; do not assume every OCI archive format is supported without a sample from the chosen exporter. Its Node coverage includes pnpm-lock.yaml and installed node_modules metadata; dev dependencies are excluded by default unless requested. A normal SDK tarball typically lacks the full resolved dependency tree, so scanning only its extracted contents cannot replace a lockfile scan. Pair exact tarball integrity/content checks with the validated revision's dependency scan or a complete, traceable SBOM. Third-party SBOM interpretation has limitations; validate component coverage. Sources: [image inputs](https://trivy.dev/docs/latest/target/container_image/), [Node coverage](https://trivy.dev/docs/latest/coverage/language/nodejs/).

Trivy YAML ignore entries support `expired_at`, package/path scoping and `statement`, but only the identifier is mandatory. The YAML format remains documented as experimental and requires explicit `--ignorefile`. Native expiry is sufficient for stopping an old suppression; a separate small policy validator is needed if every exception must have an owner, reason, expiration and bounded scope. Source: [Trivy filtering](https://trivy.dev/docs/latest/configuration/filtering/).
